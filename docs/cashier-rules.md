# Правила видеоанализа кассового узла

Пайплайн `app.services.video_analyzer:analyze_video` связывает OpenCV/YOLO,
геометрию сцены, временной `RuleEngine` и существующий JSON API. Движок работает
с наблюдениями, а не с догадками по длительности присутствия человека.
Один работающий кассир — нормальное состояние `no_violation`.

## Геометрия

Координаты заданы для камеры 464×848 и пропорционально пересчитываются для
другого разрешения того же ракурса. Для новой камеры нужна повторная калибровка.

- Бокс отбрасывается, если `x2 < 70`, **или** ширина `< 65`, **или** высота `< 120`.
  Здесь выбрано `OR` из подробного правила задания; его сводная таблица содержала
  противоречащее ему `AND`. Бокс `[1.1, 221.7, 56.3, 291.6]` отфильтровывается.
- Дверь: центр `x = 70..160`, `y = 150..420`.
- Кассир: центр `y > 450`, `x > 120`.
- Клиент: центр `x > 100`, `y = 150..450`, вне дверной зоны.
- Люди вне этих зон не включаются в число клиентов. Зоны двери и клиента
  взаимоисключающие, поэтому один бокс не учитывается дважды.

Это пространственный фильтр. Корреляция движения отражения и кассира не
вычисляется: для неё необходимы устойчивые траектории и отдельная проверка
на размеченных данных. Совпадение движения людей само по себе не доказывает отражение.

## Фазы и временные правила

`preparation → client_entry → identification → cash_operation → client_departure`.
После ухода клиента движок возвращается в `preparation`, сохраняя проверку
оставшихся на столе денег до новой операции. Фаза доступна как `RuleEngine.phase`.
Дверная зона также содержит выходящих людей; переход клиента со стула к двери
не считается новым входом.

| Код правила | Условие |
| --- | --- |
| `multiple_clients` | `client_count + entering_count >= 2` непрерывно **более 1,5 с** |
| `client_not_ready` | Наблюдаемый новый вход через дверь при отсутствии кассира |
| `unattended_laptop` | Ранее присутствовавший кассир отсутствует **более 4 с**, подтверждён открытый ноутбук |
| `unattended_cash` | Такое же отсутствие и подтверждённые наличные на столе |
| `unattended_safe` | Такое же отсутствие и подтверждённый открытый сейф |
| `unattended_key` | Такое же отсутствие и подтверждённый ключ в замке сейфа |
| `cash_before_id` | Наблюдаемое начало операции, приём/начало пересчёта денег при явно неподтверждённой проверке ID |
| `cash_bypassed_counter` | После наблюдаемого приёма деньги помещены в сейф, счётчик явно не работал на всём промежутке |
| `client_left_during_counting` | Наблюдавшийся клиент выходит при подтверждённой работе счётчика |
| `cash_returned_after_counting` | Принятые наличные возвращены клиенту после подтверждённого завершения пересчёта |
| `cash_left_on_table` | После наблюдаемого ухода клиента деньги подтверждаются на столе **более 5 с** |
| `foreign_object_on_table` | Подтверждён посторонний предмет на рабочем столе |

Длительность рассчитывается по секундам видео. Разрозненные срабатывания не
суммируются. Пропуск наблюдений более 2,5 с сбрасывает временные интервалы и
знание о начале операции. Повторные кадры одного эпизода не создают дубликаты;
подтверждённое окончание и новый эпизод позволяют новое срабатывание.
`VIDEO_SAMPLE_FPS` должен быть не меньше 0,5; рекомендуемое значение — 2.
При переменной частоте кадров используется время декодера, а если он не
предоставляет пригодные таймкоды — номер кадра и заявленный FPS.

Видео может начаться посреди обслуживания. В этом случае прошлые проверка ID
и пересчёт неизвестны: движок не обвиняет кассира в пропуске невидимого действия.
История ID и приёма денег относится к одной операции и сбрасывается для следующей.
Счётчик, работающий при одинокой работе кассира, сам по себе нарушением не является.

Таймкод события соответствует кадру, на котором условие уже подтверждено;
момент начала длительного состояния указан в описании. JPEG берётся из того же
декодированного кадра, без повторного позиционирования видеодекодера.

## Контракт локального CV-провайдера

Стандартные веса `yolov8n.pt` распознают людей и объекты COCO. Они не распознают
проверку ID, передачу наличных, активность счётчика или состояние замка.
Обнаруженный `laptop` не означает открытый/разблокированный ноутбук, белая карточка
не означает проверку личности. Поэтому эти признаки не заполняются автоматически.

Специализированная модель подключается через:

```dotenv
ANALYZER_CALLABLE=app.services.video_analyzer:analyze_video
VIDEO_MODEL_PATH=yolov8n.pt
VIDEO_SAMPLE_FPS=2
VIDEO_SIGNAL_PROVIDER=your_cv_package.signals:observe_frame
```

Синхронная функция `observe_frame(frame, timestamp_sec)` получает BGR-массив
NumPy и секунды от начала видео. Она возвращает словарь следующих признаков со
значениями строго `True`, `False` или `None`:

| Признак | Значение `True` |
| --- | --- |
| `id_verified` | В этой операции подтверждена проверка документа кассиром |
| `cash_handover` | Кассир принимает наличные от клиента, а не выдаёт деньги |
| `counter_active` | Счётчик банкнот работает |
| `cash_on_table` | В зоне стола находятся наличные |
| `cash_stored_in_safe` | Подтверждено помещение принятых денег в сейф |
| `cash_returned_to_client` | Подтверждён возврат принятых наличных клиенту |
| `laptop_open` | Подтверждён открытый ноутбук, требующий присмотра |
| `safe_open` | Подтверждён открытый сейф |
| `key_in_safe` | Ключ оставлен в замке сейфа |
| `foreign_object_on_table` | На рабочем столе посторонний предмет |

`False` — явное отрицательное наблюдение, `None`/отсутствующий ключ — неизвестно.
Например, `id_verified=False` означает, что провайдер способен отслеживать
проверку ID в этой операции и подтверждает, что её ещё не было. Отсутствие
карточки в текущем кадре такого вывода не даёт. Аналогично неизвестная работа
счётчика не превращается в утверждение, что деньги прошли мимо него.

Провайдер может отслеживать последовательность кадров; новый вызов анализа
должен начинать новую историю. Все модели запускаются локально. Нельзя
передавать видео и кадры внешним AI API.

## Запуск и проверка

```sh
python -m pip install -r requirements-video.txt
python -m app.worker
```

Веса `.pt` готовятся заранее; конфигурация архитектуры `.yaml` не заменяет
обученную модель и отклоняется. Отсутствующие/пустые веса, недекодируемый ролик, неверный
FPS и сбой модели завершаются ошибкой анализа. Совместимый старый путь
`app.services.analyzer:analyze_video` также вызывает реальный пайплайн.

Для тестов установите `requirements-dev.txt` и выполните `python -m pytest -q`
и `python -m ruff check .`. Тесты используют заданные наблюдения, подменённую
модель и синтетическое видео; веса и сеть им не нужны.

Пороги и связь событий с номерами Х-1…Х-40 взяты из пользовательского описания.
Заявленное покрытие 22 нарушений и 20 чистых видео ещё не измерено: в репозитории
нет подготовленного размеченного набора для такого прогона. Указанные в задании
ссылки на НБРК № 231 и ПОД/ФТ требуют отдельной проверки соответствия наблюдаемым
действиям, поэтому движок описывает подтверждённое визуальное событие без
автоматического юридического заключения. Для новой камеры, перекрывающихся
клиентов и точного направления движения потребуется калибровка и трекинг людей.
