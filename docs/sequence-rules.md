# Последовательности обслуживания: R01–R04

Реализован модуль `app.rules`: принимает историю подтверждённых событий,
сохраняет состояние обслуживания и выдаёт нарушения с таймкодами и ссылками
на события-доказательства. Имя видео не входит во входную схему. Известные
таймкоды примеров не используются.

## Что работает сейчас

| Правило | Условие |
| --- | --- |
| R01 `CUSTOMER_WITHOUT_CASHIER` | Известный клиент остаётся внутри при подтверждённом отсутствии кассира. |
| R02 `SECOND_CUSTOMER_DURING_SERVICE` | Другой клиент входит до подтверждённого выхода текущего клиента. |
| R03 `MONEY_BEFORE_ID` | Деньги переданы кассиру до завершения `ID_TRANSFER_TO_CASHIER → ID_CHECK → ID_ON_TABLE`. |
| R04 `MONEY_RETURNED_TO_CUSTOMER_AFTER_COUNTER` | `MONEY_TO_COUNTER → MONEY_FROM_COUNTER → MONEY_HELD_BY_CASHIER → MONEY_TRANSFER_TO_CUSTOMER` для одной истории денег и текущего клиента. |

R03 требует наблюдаемой истории действий с ID с начала обслуживания. Если проверку
ID могли пропустить из-за перекрытия, потери трека или низкой уверенности, отсутствие
события не доказывает нарушение. R01/R02 также требуют надёжной истории присутствия.
Подтверждённое нарушение может сопровождаться неопределённостями по другим правилам.

Физическое разделение стопки `MONEY_STACK_SPLIT` необязательно для R04. Оно может
дополнять доказательства. У возвращаемой части может быть другой `object_id`,
но тот же **подтверждённый** `money_group_id`: принадлежность к исходной стопке
должна быть установлена предыдущим модулем. Нельзя назначать один общий идентификатор
всем деньгам в кабинете. Другая стопка или другой клиент не удовлетворяют R04.

После полного нормального порядка генерируется `SCENARIO_COMPLETED`. Анализ
продолжается: возврат денег после этого состояния всё равно вызывает R04.
`SERVICE_ENDED` возникает только по подтверждённому выходу текущего клиента.
Выход второго вошедшего клиента не завершает первую сессию. Следующая сессия
получает отдельное состояние ID и денег.

## Запуск на примерах

Файлы в `config/rule_examples/` — **синтетические последовательности**, созданные
по описанным сценариям. Они не являются событиями, автоматически извлечёнными
из роликов X-1/X-2/X-3. Источник виден в ответе как `synthetic_example`.

```powershell
.\.venv\Scripts\python.exe -m app.rules.analyze config/rule_examples/normal_session.json --output data/rules/normal.json
.\.venv\Scripts\python.exe -m app.rules.analyze config/rule_examples/money_before_id.json --output data/rules/money-before-id.json
.\.venv\Scripts\python.exe -m app.rules.analyze config/rule_examples/returned_after_counter.json --output data/rules/returned.json
```

Ожидаются соответственно `no_violation`, R03 и R04. Ещё два примера:
`second_customer.json` → R02, `cashier_left.json` → R01.

## Swagger

После запуска обновлённого FastAPI доступен **POST `/api/v1/rules/evaluate`**.
Используется существующий `X-API-Key`. Нажмите Authorize, затем Try it out и
вставьте содержимое одного JSON-примера. Если сервер запущен без `--reload`,
перезапустите его в исходном терминале: Ctrl+C, затем:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Ответ содержит `verdict`, `violations`, `sessions`, `derived_events`,
`uncertainties` и `input_sources`. Возможны три вердикта:

- `violation` — подтверждено хотя бы одно правило;
- `no_violation` — правила проверены на полной наблюдаемой истории, начатые
  сценарии завершены, неопределённостей нет;
- `insufficient_evidence` — история, последовательность или идентификаторы неполны.

Этот endpoint принимает события. Загрузка видео через `/api/v1/analyze` пока
не извлекает эти события автоматически. Worker использует прежний контракт;
`insufficient_evidence` нельзя преобразовывать в `no_violation`.

## Контракт событий

Вход: `duration_sec`, `events`, `coverage`, необязательный `minimum_confidence`
(по умолчанию 0.75). Формат полностью показан в JSON-примерах и OpenAPI.

Каждое событие содержит:

- уникальный `event_id`, `type`, `start_sec`, `end_sec`;
- `sample_count ≥ 2`, ненулевой интервал наблюдения;
- `source`: `manual_annotation`, `local_tracker` или `synthetic_example`;
- `confidence` от 0 до 1;
- `person_id` для кассира, `customer_id` для клиентов и всех действий;
- `object_id` для ID/денег и `money_group_id` для действий с деньгами.

Интервал отражает подтверждение действия по нескольким наблюдениям. Поля
`sample_count`/`confidence` являются данными производителя; модуль правил
не проверяет изображения и не превращает эти числа в доказательство сам по себе.
События упорядочены по `end_sec`, время отсчитывается от начала ролика. Зависимые
действия с объектом должны идти последовательно; перекрывающиеся интервалы
не устанавливают порядок. Рамки на одном кадре не являются semantic events.

`coverage.people`, `coverage.id_actions`, `coverage.money_actions` — списки
интервалов, где соответствующая история **надёжно наблюдалась**. Запущенный
детектор или успешное чтение кадров не означают полной coverage. Закрытые рукой
объекты, пропущенные передачи, неясные треки оставляют разрывы. По умолчанию
coverage пустая. В синтетических примерах она полная по построению.

`CUSTOMER_ENTER` означает наблюдённый вход. `CUSTOMER_PRESENT` означает, что
клиент уже виден, но его вход мог предшествовать ролику; начало такой сессии
неполно. `CASHIER_EXIT` означает подтверждённый выход, `CASHIER_ABSENT` —
подтверждённое отсутствие при наблюдаемой области кабинета. Пропуск детектора
ни в одно из этих событий автоматически не преобразуется.

## Роли и текущие возможности CV

`app.cv.inspect_roles` теперь использует короткие геометрические треки. При
инициализации один реальный человек получает роль кассира согласно условию
пользователя. Если людей несколько, первый выбор кассира производится по зоне
и опорной точке. Далее роли сохраняются за `track_id`, когда люди перемещаются.
Известный клиент остаётся клиентом при исчезновении кассира из детекции.
Отражения исключаются до назначения треков.

Сопоставление использует рамки и близость координат, без распознавания лиц.
Разрыв до 2 секунд допускает продолжение трека. При долгом исчезновении кассира
новый трек может остаться `unknown`; при перекрытии людей возможны ошибки
сопоставления. Это ограниченная эвристика, которую нужно проверить на роликах.
Поля `track_id`, `track_samples` добавлены в JSON людей. Ложное исчезновение
не генерирует события выхода и не даёт R01 само по себе.

**Недостающий этап автоматического анализа видео:** текущая модель денег
обнаруживает рамки с существенными пропусками. Модели ID и надёжного распознавания
передач, взаимодействия с ID и загрузки/извлечения из счётчика пока нет.
`ID_CHECK` здесь означает наблюдаемое визуальное взаимодействие с документом;
по видео нельзя подтвердить юридическую или банковскую проверку личности.
Чтобы применять правила к реальным видео, нужно получить и проверить эти события
по трекам рук/объектов либо вручную разметить их как `manual_annotation`.

## Проверки

Тестируются полный нормальный порядок, все четыре нарушения, сохранение текущей
сессии, сброс ID между клиентами, возврат части денег без события разделения,
несовпадающие объекты/клиенты, перекрытие событий, неполная история, низкая
уверенность, краткие потери детекции, валидация API и его авторизация.
Сдвиг и масштабирование времени не меняют результат правил. Эти проверки
оценивают программную логику; точность извлечения событий из видео ими не измерена.
