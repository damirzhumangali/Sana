# Sana — backend для кейса ForteBank

FastAPI принимает видео `.mov`, сохраняет его локально и возвращает `job_id`.
API статусов и отдельный worker реализованы. Реальную функцию OpenCV/YOLO
нужно подключить от AI/CV-команды; по умолчанию анализатор не настроен.
Подробный разбор задания и план: [docs/case-analysis.md](docs/case-analysis.md).

## Запуск в Windows / PowerShell

Используем Python 3.11+; локальное окружение для этого проекта создано на Python 3.12.
Версию Python для OpenCV/YOLO согласуйте с командой перед подключением моделей.
Все команды выполняются из корня проекта.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(32))"
```

Вставьте сгенерированный ключ в `API_KEY` внутри `.env` вместо заглушки.
Ключ обязателен; с пустым ключом или заглушкой сервер не запустится.
Если окружение и зависимости уже созданы, начните с настройки `.env`.
Для запуска без инструментов разработки достаточно `requirements.txt`.

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

- Swagger UI: http://127.0.0.1:8000/docs — нажмите **Authorize**, введите ключ, затем загрузите файл.
- Проверка сервера: http://127.0.0.1:8000/health — без ключа.
- Остановка: `Ctrl+C`.

Если Swagger показывает `Failed to fetch`, сначала откройте
http://127.0.0.1:8000/health. Если адрес недоступен, проверьте терминал Uvicorn:
процесс должен продолжать работать. Запустите сервер командой выше, затем
обновите http://127.0.0.1:8000/docs, снова выполните **Authorize** и выберите файл.
При изменении `.env` перезапустите сервер вручную.

Используйте один адрес для документации и API: `http://127.0.0.1:8000`.
Не открывайте Swagger через другой хост, порт или HTTPS-прокси без соответствующей
настройки. Для Swagger и API с одинаковыми схемой, хостом и портом CORS не требуется:
[документация Swagger](https://swagger.io/docs/open-source-tools/swagger-ui/usage/cors/).
Сообщение `Failed to fetch` само по себе не определяет причину. Если `/health`
работает, но загрузка не проходит, сохраните сообщение из консоли браузера
и вывод терминала Uvicorn в момент запроса, скрыв API-ключ.

## Загрузка видео

```powershell
$apiKey = "ваш-ключ-из-.env"
curl.exe -X POST "http://127.0.0.1:8000/api/v1/analyze" -H "X-API-Key: $apiKey" -F "file=@C:/path/to/video.mov"
```

Ответ `201 Created`:

```json
{"job_id":"969750d3-9c92-4c11-903a-5bb229e86a9a"}
```

Загрузка использует `multipart/form-data`, имя поля строго `file`.
`job_id` возвращается после сохранения файла и записи SQLite. Он не означает, что
анализ уже выполнен или запущен. Внутренний статус ожидающей задачи — `uploaded`;
наружу ожидание и выполнение выдаются как `processing`.

| Код | Значение |
| --- | --- |
| 201 | Файл и задача сохранены |
| 400 | Расширение не `.mov` или файл пустой |
| 401 | Нет верного `X-API-Key` |
| 413 | Превышен лимит размера |
| 422 | Нет обязательного поля `file` или неверный формат запроса |
| 503 | Не удалось сохранить файл или запись задачи |

Принимаются `.mov` и `.MOV`. MIME-тип не ограничен: клиенты могут передавать видео
как `application/octet-stream`. На этом этапе проверяются расширение и размер;
декодирование и проверка содержимого появятся с OpenCV. Переименованный текстовый
файл пока тоже будет принят — это ещё не проверка корректности видеоконтейнера.

## Получение состояния задачи

После обновления кода перезапустите API и обновите `/docs`. Откройте
`GET /api/v1/jobs/{job_id}`, нажмите **Try it out**, вставьте UUID из ответа
загрузки и выполните запрос. Ключ требуется так же, как для загрузки.

```powershell
curl.exe "http://127.0.0.1:8000/api/v1/jobs/UUID-ИЗ-ОТВЕТА-ЗАГРУЗКИ" -H "X-API-Key: $apiKey"
```

Пока задача ожидает worker или выполняется:

```json
{"job_id":"969750d3-9c92-4c11-903a-5bb229e86a9a","status":"processing"}
```

После успешного анализа без событий:

```json
{
  "job_id": "969750d3-9c92-4c11-903a-5bb229e86a9a",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

При ошибке выполнения:

```json
{
  "job_id": "969750d3-9c92-4c11-903a-5bb229e86a9a",
  "status": "failed",
  "error": {"code": "JOB_TIMEOUT", "message": "Video analysis exceeded its time limit"}
}
```

Все три состояния возвращаются с HTTP `200`: запрос состояния выполнен успешно,
даже если сама задача завершилась ошибкой. Неизвестный UUID → `404`, некорректный
UUID → `422`, неверный ключ → `401`, недоступное хранилище → `503`.
В ответах нет путей к файлам, токенов worker или внутренних трассировок.

## Worker и подключение AI-команды

Worker — отдельный процесс. Он забирает задачи из SQLite, запускает локальный
обработчик и сохраняет результат. Одну задачу нельзя одновременно закрепить
за двумя worker. Результат и окончательный статус записываются одной транзакцией.

Обработчик подключается переменной в `.env`:

```dotenv
ANALYZER_CALLABLE=your_cv_package.pipeline:analyze_video
JOB_TIMEOUT_SECONDS=240
WORKER_POLL_SECONDS=1
```

`your_cv_package.pipeline:analyze_video` — пример пути к модулю и функции вашей
команды, а не уже существующий обработчик. Модуль должен импортироваться из
корня проекта. Формат функции и результата: [docs/ai-integration.md](docs/ai-integration.md).

После подключения настоящего обработчика запустите во втором терминале:

```powershell
.\.venv\Scripts\python.exe -m app.worker
```

API и worker запускаются из одного корня проекта с одинаковым `STORAGE_DIR`.
После изменения кода AI или его настроек перезапустите worker.

Без `ANALYZER_CALLABLE` worker завершается с объяснением и кодом `2`, не забирая
задач. Ожидающая задача остаётся `processing`, пока обработчик не подключён
и worker не запущен. В приложении нет автоматического фиктивного вердикта.

Каждая задача выполняется в отдельном дочернем процессе, совместимом с Windows
через `spawn`. При таймауте процесс завершается; следующий файл может обрабатываться
дальше. На этом этапе обработчик и веса загружаются заново для каждой задачи;
оптимизацию постоянного процесса с моделью будем делать по замерам AI-команды.

`JOB_TIMEOUT_SECONDS` отсчитывается от захвата задачи worker и включает запуск
дочернего процесса, импорт модели и запись результата. Это пока не гарантия
общего времени до 5 минут: ожидание в очереди ещё не ограничено. Ограничение
очереди и общий бюджет добавим перед публичным запуском.

Если worker аварийно завершится, уже захваченная задача станет `failed` после
своего дедлайна при следующем запросе состояния либо следующем проходе worker.
Автоматического повторного анализа нет. Запоздавший результат не перезапишет
ошибку таймаута или уже завершённый результат.

Основные коды ошибок задач: `INVALID_RESULT`, `ANALYZER_ERROR`, `VIDEO_NOT_FOUND`,
`JOB_TIMEOUT`, `WORKER_ERROR`, `WORKER_INTERRUPTED`.

## Хранение и настройки

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `API_KEY` | Секрет в заголовке `X-API-Key` | Обязателен |
| `STORAGE_DIR` | Локальная папка данных | `data` |
| `MAX_UPLOAD_MB` | Максимальный размер одного файла в МиБ | `100` |
| `ANALYZER_CALLABLE` | Локальная функция анализа в формате `module:function` | Не задана |
| `JOB_TIMEOUT_SECONDS` | Лимит выполнения задачи с момента захвата worker, секунды | `240` |
| `WORKER_POLL_SECONDS` | Пауза worker, если нет ожидающих задач, секунды | `1` |

Настройки читаются из `.env` и переменных окружения; окружение имеет приоритет.
Относительные пути считаются от рабочей папки запуска.

Файлы: `data/uploads/<job_id>.mov`. Метаданные: `data/jobs.sqlite3`.
Исходное имя не используется в пути. Повторные загрузки получают разные UUID.
Файлы и записи сохраняются между перезапусками. Если обычная операция сохранения
завершается ошибкой, частичный файл удаляется; аварийное завершение процесса
может оставить файл без записи. Периодическую сверку и очистку добавим отдельно.
Схема SQLite обновляется автоматически с сохранением старых загрузок.
Worker использует `data/work/` для временной передачи JSON из дочернего процесса
и удаляет эти файлы при обычном завершении, ошибке или таймауте. После аварийного
завершения самого worker временный JSON может остаться до будущей очистки.

Файл копируется блоками по 1 МиБ из `UploadFile`; multipart-парсер FastAPI может
временно сохранять входящий файл до вызова обработчика. Лимит этого этапа
проверяется при копировании в постоянное хранилище. Перед публичным запуском
добавим ограничение тела запроса на уровне reverse proxy, защиту до чтения тела,
лимиты одновременных задач и политику удаления видео.

`.env`, видео, веса моделей и `data/` исключены из Git. Публичная раздача
папки загрузок не настроена. Не добавляйте данные кейса в репозиторий.

## Первый шаг CV: кассир и клиент

Отдельная диагностическая команда читает локальное видео. YOLO находит людей
(класс `person`). При первом назначении единственный реальный человек считается
кассиром. Если людей несколько, выбирается максимум один человек в зоне кассира,
ближайший к `--cashier-anchor 0.48 0.57`. Когда кассир определён и виден, остальные
реальные люди получают роль `customer`. Далее роли сохраняются на геометрических
треках; неразрешённые роли остаются `unknown`. Зоны настроены для
ракурса предоставленных роликов в `config/fortebank_camera.json`; если ракурс
изменится, проверьте и поправьте координаты от 0 до 1.

1. Установите дополнительные зависимости, когда доступен Python Package Index.
   В этом окружении `pip` запускается с `PIP_NO_INDEX=1`, поэтому его нужно
   переопределить для установки:

   ```powershell
   $env:PIP_NO_INDEX = '0'
   .\.venv\Scripts\python.exe -m pip install -r requirements-cv.txt --index-url https://pypi.org/simple
   ```

2. Проверьте зоны на одном видео до установки или запуска YOLO:

   ```powershell
   .\.venv\Scripts\python.exe -m app.cv.inspect_roles "C:\Users\dilda\Downloads\open\open\videos\X-1.mov" --preview-only
   ```

   Откройте `data/roles-preview.jpg`. Зелёная зона соответствует кассиру,
   синяя — клиенту. Кадр можно изменить через `--preview-seconds 10`.

3. Один раз получите локальные веса модели при доступном интернете:

   ```powershell
   .\.venv\Scripts\python.exe -c "from ultralytics import YOLO; YOLO('yolo11n.pt')"
   ```

   Проверьте лицензию кода и весов до использования в итоговой сдаче.

4. Запустите определение людей и ролей:

   ```powershell
   .\.venv\Scripts\python.exe -m app.cv.inspect_roles "C:\Users\dilda\Downloads\open\open\videos\X-1.mov" --model yolo11n.pt
   ```

   `data/person-roles.json` содержит время каждого проверенного кадра,
   прямоугольники людей, уверенность модели и роль по зоне. На
   `data/roles-preview.jpg` видны найденные люди на кадре около пятой секунды.
   По умолчанию анализируются 2 кадра
   в секунду; `--sample-fps 4` повышает частоту. Не используйте результат
   `unknown` как подтверждение, что человека не было. Отражения в стекле
   всё ещё иногда дают дополнительные прямоугольники; перед детекцией
   нарушений нужна проверка на нескольких роликах.

Команда пока не подключена к `app.worker`: присутствие кассира и клиента само
по себе не доказывает нарушение. Следующий шаг — проверить точность детекции
на нескольких роликах, затем реализовать конкретное визуальное событие и его
доказательные кадры.

### Фильтрация отражений

`reflection_regions` в `config/fortebank_camera.json` задаёт области стекла
для текущего ракурса. Если не менее 97% площади рамки человека находится
внутри одной такой области, находка получает `visibility: reflection_candidate`
и `counted: false`. Она остаётся в `people` для проверки, но не учитывается
в `person_count`, `customer_count` и `cashier_present`. На проверочном кадре
предполагаемые отражения показаны серыми рамками с подписью `reflection?`.
Общее число исключённых находок на кадре — `reflection_candidate_count`.

Исходное изображение не закрашивается. Простое пересечение рамки со стеклом
не исключает человека, стоящего перед ним. Это геометрическая эвристика:
реальный человек, чья рамка целиком окажется внутри отмеченной области,
тоже может быть исключён. При новом ракурсе области нужно настроить заново;
пустой список `reflection_regions: []` отключает фильтр. Проверьте случаи
одного человека, нескольких людей, входа и движения перед стеклом.

Проверка на локальных роликах (частота выборки 2 кадра/с):
- `Х-14`, около 5 с: две рамки → один учитываемый человек и одно отражение;
- `Х-18`, около 5 с: три рамки → два учитываемых человека и одно отражение;
- `Х-18`, около 20 с: все три реальных человека сохранены;
- `X-1`, около 5 с: оба реальных человека сохранены.

Это проверка конкретных кадров, а не оценка точности на всём наборе.
Назначение ролей по зонам остаётся отдельным ограничением: сидящий клиент
может попасть в зону кассира, а отражения вне заданных областей останутся.

Правило «один кассир, остальные клиенты» соблюдается в каждом кадре после фильтрации
отражений. `unknown_role_count` показывает количество людей с неопределённой ролью.
Добавлено короткое геометрическое сопровождение: первоначально единственный
реальный человек считается кассиром; далее роли сохраняются за `track_id`.
Если первоначально людей несколько, кассир выбирается по зоне и опорной точке.
Известный клиент не становится кассиром при пропуске детекции кассира. Долгие
перекрытия и возвращение после потери трека остаются ограничениями. Опорная точка
задаётся в долях ширины/высоты; распознавание лиц не применяется.

## Правила последовательности обслуживания

Добавлен `app.rules` и **POST `/api/v1/rules/evaluate`** в Swagger: клиент без
кассира (R01), второй клиент во время обслуживания (R02), деньги до завершения
работы с ID (R03), возврат денег клиенту после счётчика (R04).

```powershell
.\.venv\Scripts\python.exe -m app.rules.analyze config/rule_examples/returned_after_counter.json
```

Команда проверяет синтетическую последовательность и возвращает R04. Для входа
нужны подтверждённые события, идентификаторы и интервалы надёжного наблюдения.
Для реального видео теперь есть отдельный запуск `app.cv.analyze_events`:
детекции → история треков → события → этот же Rule Engine. Детектор ID пока
недоступен; уверенно восстановить денежные действия текущие веса ещё не позволяют.
Неполная история даёт `insufficient_evidence`. Полный контракт и все примеры:
[docs/sequence-rules.md](docs/sequence-rules.md).

## Видео → события → правила

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m app.cv.analyze_events "C:\Users\dilda\Downloads\open\open\videos\Х-3.mov" --output-dir data/events/x3
```

В `data/events/x3/` появятся `debug.mp4`, `timeline.txt`, `events.json`,
`track_history.json`, `rule_request.json` и `rule_result.json`. Команда работает
локально на CPU и сама вызывает существующий Rule Engine. Сервер для неё не нужен.
Зоны и временные пороги: `config/event_camera.json`.

На проверенных реальных X‑3, X‑2, X‑1 итог — `insufficient_evidence`:
подтверждены присутствие кассира, вход клиента и начало обслуживания, но не полная
последовательность ID/денег. Это не заключение об отсутствии нарушений.
Запуск, повторная обработка без YOLO, устройство и ограничения:
[docs/video-events.md](docs/video-events.md).

Подробный разбор сбоев денежной цепочки по каждому событию, сравнение до/после
фильтрации дублей и проверка исправленного детектора:

## Видимые деньги: локальный прототип

В стандартных весах `yolo11n.pt` с классами COCO нет класса денег. Для него нужен
отдельный обученный файл. `app.cv.inspect_cash` проверяет наличие класса `cash`
и не принимает обычные веса для людей вместо денежных весов.

На этом компьютере подготовлены предварительные рамки денег в
`data/cash/annotations.json`. Разметка сделана по видимым кадрам и требует проверки
человеком. Метки нарушений из Excel не заменяют рамки купюр. Файлы видео, разметки,
весов и результатов находятся локально и исключены из Git.

Текущий файл `data/cash/models/cash.pt` обучен на 33 кадрах (25 рамок). Выбраны
веса последней эпохи `cash_v2/weights/last.pt`: на 9 кадрах валидации при пороге
0.25 они дали 2 верные рамки, 2 ложные рамки и 1 пропуск; автоматически выбранный
`best.pt` при том же запуске давал больше ложных рамок. На независимых 7 кадрах
из двух других роликов: 2 верные рамки, 0 ложных, 4 пропуска. Эти результаты
относятся к предварительной разметке; 1 отрицательного тестового кадра недостаточно
для оценки частоты ложных срабатываний. Прототип пока часто пропускает деньги в
руках. Это рабочая основа для доразметки и обучения, качество для нарушений ещё
недостаточно. Подробности: `data/cash/models/model-card.json`.

### Запуск

Из корня проекта после подготовки `data/cash/models/cash.pt`:

```powershell
.\.venv\Scripts\python.exe -m app.cv.inspect_cash "C:\Users\dilda\Downloads\open\open\videos\Х-38.mov"
```

Буква `Х` в имени этого ролика кириллическая. По умолчанию анализируются примерно
2 кадра/с на CPU, размер входа 768, порог уверенности 0.25. Поиск охватывает весь
кадр, включая руки, стол, область мешка и сейфа. Координаты стола не ограничивают
детекцию. Для быстрых движений можно указать `--sample-fps 5`.

Результаты в `data/cash/results/Х-38/`:

- `annotated.mp4` — видео с рамками, без звука, с частотой выбранных кадров;
- `preview.jpg` — кадр с наиболее уверенной находкой, либо первый кадр без находок;
- `detections.json` — таймкоды, рамки в пикселях исходного кадра, оценки уверенности,
  параметры и SHA256 использованных весов.

Повторный запуск в ту же папку заменяет эти три результата. Другую папку можно
задать через `--output-dir data/cash/results/my-check`. Для короткой проверки есть
`--max-seconds 10`. Статус `not_detected` означает отсутствие находки модели:
деньги могут быть скрыты, слишком малы или пропущены. Детектор пока не определяет
сумму, владельца, источник денег, факт передачи и нарушение. Уверенность YOLO
не является гарантированной вероятностью правильного ответа.

Модуль `inspect_cash` запускается отдельно от Swagger и worker. Сопровождение денег,
временные события и проверка R01–R04 доступны в `app.cv.analyze_events` (см. выше).
Отслеживания кистей рук и состояния сейфа пока нет. Наличие денег само по себе
не даёт вердикта.

### Обучение и проверка

```powershell
# Экспорт в НОВУЮ папку: кадры одного исходного видео не попадут в разные выборки.
.\.venv\Scripts\python.exe -m app.cv.cash_dataset data/cash/annotations.json --output data/cash/dataset-new

# Локальные базовые веса должны уже существовать. Обучение на CPU занимает время.
.\.venv\Scripts\python.exe -m app.cv.train_cash --data data/cash/dataset-new/cash.yaml --base yolo11n.pt --epochs 60 --name my-cash

# Явно выбираем веса для следующего запуска анализа.
New-Item -ItemType Directory -Force data/cash/models
Copy-Item data/cash/runs/my-cash/weights/best.pt data/cash/models/cash.pt

# Сначала настройка на val, затем независимая проверка на test.
.\.venv\Scripts\python.exe -m app.cv.evaluate_cash --split val
.\.venv\Scripts\python.exe -m app.cv.evaluate_cash --split test
```

Формат разметки: объект `class: "cash"` и массив `items`; у каждого кадра есть `id`,
`split` (`train`, `val`, `test`), путь `video`, `video_sha256`, путь `image`, размеры
`width`/`height`, `timecode_sec`, `review` и `boxes` в пикселях `[x1,y1,x2,y2]`.
Экспортируются только статусы `reviewed` и `reviewed_provisional`. Пустой список
рамок — явно проверенный кадр без видимых денег. `null` и непроверенные кадры
не превращаются в отрицательные примеры. Неясные кадры исключаются. Одну стопку
соприкасающихся купюр размечают одной рамкой; отдельные стопки — отдельно.

`evaluate_cash` считает совпадение при IoU ≥ 0.5, сохраняет JSON и кадры в
`data/cash/evaluation/`: зелёные рамки — предсказания, розовые — разметка. Здесь
precision — доля верных рамок среди найденных, recall — доля найденных размеченных
объектов. Маленькая предварительная выборка не подтверждает качество на новых
камерах. Для улучшения добавляйте реальные кадры с купюрами в руках и у сейфа,
а также похожие предметы без денег: документы, телефон, кружку и счётную машинку.
